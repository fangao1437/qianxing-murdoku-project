## 一、实现层面的完整规则（代码事实）

> 关键文件：lua/murdoku_core.lua（纯规则）、lua/room_map.lua（房间/墙）、
> tools/design_rules.lua（设计期结构规则）、tools/design_solve.lua（设计期求解器）。
> 运行时（打进 dist 的）没有 design_rules / design_solve。

### 1.1 摆位（rules 表）

| 规则 | 默认 | 含义 | 代码位置 |
|---|---|---|---|
| one_per_row | true | 每行最多 1 人（只有显式 false 才关） | Core:rules（:1542-1550）、Core:violations（:1578） |
| one_per_col | true | 每列最多 1 人 | 同上 |
| one_per_room | false | 每房间最多 1 人（默认关；现有四关都关） | 同上 |
| place_all | true | 所有 suspects 声明过的棋子都必须摆上 | Core:submit（:2376-2406） |

- 摆上 = select_suspect(id) + hold_cell(r,c)；同一棋子换格 = 等效「撤销后重放」（核心里自动处理）。
- 不可站人的格子：level.blocked 里列的格 + 所有 objects 中 occupiable=false 的家具格。
  这些格放不了人（do_place 拒绝），但可以打 X / 打笔记（X 与笔记是推理痕迹，不受 blocked 限制）。
- 摆位约束在运行时只被 submit 检查（violations 只看行/列/房间超员；place_all 只看是否所有棋子摆上）。
- 每行/列「恰好 1 人」不是代码保证，而是「N×N 棋盘 + N 枚棋子 + one_per_row/col + place_all」
  的数学推论（设计约定；见 §5.4）。

### 1.2 房间 / 墙 / 门 / 区域相邻

- 坐标：r = 行 1..rows（上→下），c = 列 1..cols（左→右）。
- 墙写法与语义：
  · {"v", r, c} 挡 (r,c) ↔ (r,c+1)；
  · {"h", r, c} 挡 (r,c) ↔ (r+1,c)。
- 房间 = 只看墙做洪水填充（room_map.lua:58-84 compute_rooms），与门无关；房间号从 1 开始、
  按「行优先扫描 + 栈式洪泛」的顺序编号（改墙可能重排房间号，不要把房间号当稳定引用）。
- 门写法与墙完全一致，同粒度；不改变房间划分，只建立「区域相邻」图：
  · 区域 X、Y 相邻 ⟺ 门所在的那条格边两侧恰好是 X 与 Y（不经过第三个区域）；
  · 关系是双向的（link 两边都写）；
  · 门若开在两个同一区域的格之间（边不是墙），不会产生任何相邻（link 里 a==b 被忽略）；
  · 门若开在外框边上，compute_room_adjacency 只扫内部边，等于无效。
- 代码：M.build_walls / M.compute_rooms（core:121-131 转调 room_map）、
  M.build_doors（core:138-163）、M.compute_room_adjacency（core:167-188）。
- 注意事项（重要坑）：
  · validate_level 对 walls 完全不做格式/越界校验（写错=静默忽略）；
  · doors 只校验「数组形式 + r,c≥1」，不校验上界、不校验该边是否真的有墙、不校验落在内边；
  · 房间号不稳定 ⇒ 线索里尽量别用 in_room / room_has / room_size_hint 的绝对房间号，
    非要用就先结构报错核对（structure_report 会给出受害者区域号）。

### 1.3 受害者（victim）

- 两种写法：
  · victim = { id = "V" }（推荐）⇒ V 必须同时出现在 suspects 里，受害者也要摆上棋盘；
  · victim = { r=, c= } ⇒ 受害者固定占一格（不在 suspects 里）。
- 受害者算「人」：房间人数、alone 类线索、count_in_room 都把它算进去。
- 受害者位置只影响线索判定与 R3；运行时的受害者视图从 core.pos[victim_id] 取。
- 已知小缺陷（坑）：Core.new 里 self.roles.victim = self.victim_id 那一行在 victim_id 赋值之前，
  所以 core.roles.victim 恒为 nil、view().roles.victim 也恒 nil。要受害者 id 请用 core.victim_id。【读代码推断】

### 1.4 盗窃者 / 同伙（roles）

- roles.thief 必填，且必须在 suspects 里、不能是受害者。
- roles.accomplice 可空；写了就必须在 suspects 里、≠ thief、≠ 受害者。
- 运行时结案判据（Core:accuse_verdict，:2418-2462）：
  先 submit()（行/列/房间超员 + place_all），通过后比较
  「thief_id == roles.thief」且「has_accomplice == (roles.accomplice ~= nil)」且
  （无同伙 或 accomplice_id == roles.accomplice）⇒ 胜。
- 玩家不输入答案：UI 的 do_submit 在 submit 通过后直接把关卡 roles 填进去当玩家答案
  （ui_controller.lua:559-567）。⇒ 本作当前是「摆位成立即胜」，线索与 thief 身份不参与运行时判定。
- 「受害者房间里还有别人（k≥2）⇒ 必有同伙 / 同伙必须同区」两条规则已废止
  （2026-10-18；见 design_rules.lua:4-14,121-142）。旧文档/旧关卡头部注释里的这套说法全部过时。

### 1.5 谎言（meta）

- meta.false_clue = 第几条卡线索是假的（1 起，按 level.clues 数组序号）；不写 = 本关没有假话。
- 引擎里由它推出 core.allowed_false = 1 或 0（murdoku_core.lua:1359）；
  运行时不使用 allowed_false；它只被设计期求解器 tools/design_solve.lua 使用。
- meta.announce ∈ none / one / unknown（validate 校验枚举）。
  ⚠️ 2026-10-18 起副标题控件被删，announce 那行提示已无显示出口（ui_controller.lua:2426-2440）；
  当前 announce 只是数据字段 + 校验用。【读代码推断】
- 「假话粒度 = 整条线索，至多 1 条」；validate_levels 的假话检查只看卡线索（clue_results），
  通用线索（general_clues）不参与 false_clue 序号，也不能被声明成假话（声明了也永远对不上）。
  但设计期求解器把通用线索也算进 allowed_false 的违反条数 ⇒ 两边口径有细微不一致（坑）。
- 使用角色别名 @accomplice 的线索在「本关没有同伙」时：resolve 得 nil ⇒ 判定 false，
  天然是「要么真有同伙，要么这句是假话」。【读代码推断】

### 1.6 判据（submit / accuse）完整链路

~~~~text
玩家摆子 → UI「提交」→ Controller:do_submit
  → Core:submit():
       violations = rows/cols/rooms 超员（Core:violations）
       missing    = 还有哪些声明过的棋子没摆上
       ok = (#violations == 0) and (not place_all or #missing == 0)
       （线索结果只放进 result.clues 供离线调试，不参与 ok；reveal 恒 false）
  → 若 ok：Controller 直接把 core.roles（关卡写死的答案）填进 finish_accuse
  → Core:accuse_verdict(roles.thief, roles.accomplice ~= nil, roles.accomplice)
       → 再跑一次 submit；通过后比较三者 ⇒ 胜 / 败（败了给出「N/M 位置正确」）
~~~~

- 结论：运行时对「线索是否成立」「摆位是否等于 solution」零校验。
  一个只满足行/列的摆位（哪怕与线索全矛盾）也能提交通过并结算胜利。【已实测：把 case_001 答案里
  A 与 V 换位（合法行列）后 submit().ok = true，failed_clues = [1,3]，随后自动指认仍判胜】
- 关卡设计必须靠设计期保证：答案自洽、线索可推、最好唯一。

### 1.7 结构规则 R3 / R4 的现状（只在设计期）

实现：tools/design_rules.lua（把它 require 进来才会挂到 Core 上；validate_levels 已 require）。
structure_report(roles) 的判定（design_rules.lua:56-142）：

1. 必须有 roles.thief；
2. 受害者必须已摆上（core.pos[victim_id] 或 victim_fixed），否则报错；
3. 受害者区域 Rv 必须至少有一个门相邻区域，否则报「R3 无法成立」；
4. 对每个相邻区域 X 统计「无辜人数」inno(X) = X 内既不是 thief 也不是 accomplice 的人数
   （注意：按代码，受害者如果在该区也计入「无辜」，因为只排除 thief/accomplice）；
5. 相邻区域中 inno 最大的区域集合 best_rooms：若并列且 tie_policy=forbid ⇒ 报错；
6. 盗窃者必须已摆上、所在区域 ∈ Adj(Rv)、且必须是 best_rooms 之一（严格最大，除 tie_policy=allow）；
7. 若声明了 accomplice，则同伙必须已摆上；不再要求同区（旧 R4 已删）；
8. k = 受害者区域内总人数，只作为 info 返回，没有任何阈值规则；
9. 返回 ok, errors, info（info 含 victim_room / adjacent / innocent_counts / best / best_rooms /
   k / thief_room / has_accomplice）。

- tie_policy 只在设计期被读：运行时提交/结算完全不看它。
- 设计手册「区域相邻数 ≥ 2」不在代码里（只要求 ≥1）；当前 case_002 受害者区域只有 1 个相邻区，
  结构照样 OK，但 R3 的比较退化成废话。
- 旧 R4（k≥2 ⇒ 必有同伙；同伙必须同区）已彻底删除，不要再用它当教学点。

## 二、线索类型全目录（60 种，注册表实测）

> 来源：Core.clues 注册表（murdoku_core.lua:198 起逐个 reg 注册）+ 我枚举运行结果。【已实测：共 60 种】
> 三种角色别名可写在 who / a / b 上：@thief / @accomplice / @victim（ROLE_ALIASES，core:30-34）。
> 通用约定：
>   · 判定返回 false 的情形包括「引用的棋子还没摆上」（ctx.pos 为 nil ⇒ 绝大多数类型 false）；

>   · 「提示」列 = Core:clue_hint 会不会给位置提示（hint_for，core:1749-1767）。

### 2.11 ★ 一行一列约束下的「退化清单」（写关卡前必看）

本作开 one_per_row + one_per_col + place_all，且盘面 N×N、N 枚棋子 ⇒ 任何完整摆位都是
「每行恰好一人、每列恰好一人」的排列。由此：

A. 恒假（只能拿来当假话，不能当有效线索）〔读代码推断 + case_001 答案上已实测〕

- left_of / right_of / above / below（要求同行或同列）
- between（要求同行或同列夹在中间）
- beside（人对人：要求四邻 ⇒ 必须同行或同列）
- in_front_of（人对人：要求正交相邻）
- with_victim（要求同格）
- distance 的 d=1（唯一相邻距离；两人四邻不可能）

B. 恒真 / 无信息（写了等于没写）

- not_beside：两人都已摆上时恒真
- only_one_in_row：满盘时每行恒为 1 ⇒ 恒真
- nobody_in_water：water 列表为空时恒真

C. 可用但语义要小心

- distance：可用距离 d 必须 ≥ 2（d=2..2*(N-1)）
- same_room / different_room / alone* / room_has / in_room：依赖房间划分与房间号；改墙会使房间号变化
- on_object / only_on_object：家具必须 occupiable=true（否则永远假）

### 2.12 位置提示规则（Core:clue_hint，core:1749-1792）

选中线索卡时棋盘高亮「这条线索允许这个人出现的位置」；只算可站人的格、与当前摆位无关。

| 线索类型 | 提示高亮 |
|---|---|
| on_object / only_on_object / one_on_object / n_on_object / nobody_on_object | 该家具自己的格子（可站才进集合） |
| beside_object / only_beside / not_beside_object | 该家具四邻、同房间、可站的格 |
| in_col | 该列可站格 |
| in_row | 该行可站格 |
| at | 该格本身（可站才给） |
| 其它全部类型（人对人/房间级/身份级/全局） | nil（不做提示） |

- 线索类型拼错或未注册 ⇒ hint 返回 nil（不报错、静默无提示）；validate_level 会拦住卡线索与通用线索的类型拼错。
- 假话也可以有提示；「假话不靠提示暴露」在代码里没有强制（只是设计约定）。

### 2.13 卡片文案：源码 text() 只是回退

- 每种线索类型自带 text(ctx,cl) 渲染文案（例：「收藏家 在第5列」），view().clues[i].text 就是它。
- 但真机卡片优先用编辑器 row.<关>.<行> 的 who/what/letter/face 四槽位；
  只有没配 row 内容时才回退到「从 text 里切人名」：
  split_by_name 找 tray 里最长匹配的显示名 ⇒ 名字/前缀/后缀/该人 id/头像（ui_controller.lua:2071-2085, 5718-5837）。
  回退结果：who=前缀+名字、what=名字之后的部分、letter=该人 id、portrait=tray 头像。
- 结论：线索内容设计要以「row 区手工文案」为准；源码 text() 只用于离线 dump/测试与兜底。

### 3.2 rules / walls / doors 的写法

rules：

~~~~lua
rules = {
  one_per_row  = true,
  one_per_col  = true,
  one_per_room = false,
  place_all    = true,
  tie_policy   = "forbid",   -- 设计期结构闸门用；forbid / allow
}
~~~~

walls 与 doors 都支持三种写法（room_map.build_walls / core.build_doors 都认）：

~~~~lua
-- A：数组（validate/文档主推，doors 只有这种写法会被 validate 检查）
walls = { { "v", 1, 3 }, { "h", 3, 2 } }
-- B：按方向分组，元素为 {"r","c"} 字符串
walls = { v = { { "1", "3" } }, h = { { "3", "2" } } }
-- C：按方向分组，元素为 "r:c" 字符串
walls = { v = { "1:3" }, h = { "3:2" } }
~~~~

语义（再强调一次）：
- {"v", r, c} = (r,c) 与 (r,c+1) 之间竖墙；{"h", r, c} = (r,c) 与 (r+1,c) 之间横墙。
- walls 决定房间划分（洪泛）；doors 只建相邻图、不改房间。
- doors 用分组写法时 validate_level 会看不见（length 0），core 仍能解析 ⇒ 能跑但没校验；建议一律数组写法。
- 墙/门坐标必须落在真实存在的相邻格对上；越界会被静默忽略（v 的 c 必须 ≤ cols-1，h 的 r 必须 ≤ rows-1）。

### 3.3 objects（家具）与可站性

~~~~lua
objects = {
  -- 完整写法（推荐）：cells + occupiable + kind
  ["桌子"] = { cells = { { r=1, c=1 }, { r=2, c=1 } }, occupiable = false, kind = "table" },
  ["地毯"] = { cells = { { r=3, c=1 }, { r=3, c=2 } }, occupiable = true,  kind = "carpet" },
  -- 简写：直接给格子数组 ⇒ 可站
  ["椅子"] = { { r=4, c=2 }, { r=5, c=4 } },
}
~~~~

- occupiable = false ⇒ 该家具所有格自动加入 blocked（放不了人）；不写 = 可站。
- kind = 界面层查素材用的键（ui_controller.object_key_of：obj.<kind>）。当前四关用过的 kind：
  table / plant / carpet / chair / shelf / statue / case。新 kind 不一定有素材 ⇒ 建议复用。
- 中文家具名必须写成 ["名"] = ...（Lua 标识符只能 ASCII）。
- 多格家具 = cells 里多个坐标；线索 beside_object / on_object 等按整套格子判定。
- 家具格**可以**同时被多个线索引用；也可以落在不同房间（代码不禁止，但 beside 同室判定会让语义变怪）。

### 3.4 blocked / water

- blocked = { {r,c}, ... }（或 {r=,c=}）⇒ 这些格不能站人。用于家具之外的手工限制。
- water = { {r,c}, ... } ⇒ 只被 nobody_in_water 线索读取；不影响摆位（代码不禁止人站水里）。
- 两处坐标都走 as_pos：支持 {r=,c=}、{r,c} 数组、"r:c" 字符串。

### 3.5 suspects / victim / portrait / gender

~~~~lua
suspects = {
  { id = "A", name = "值夜保安", portrait = "portrait.A", gender = "male" },
  { id = "B", name = "布展助理", portrait = "portrait.B", gender = "female" },
  { id = "C", name = "外聘搬运工", portrait = "portrait.C", gender = "male" },
  { id = "D", name = "首席鉴定师", portrait = "portrait.D", gender = "male" },
  { id = "E", name = "跟拍记者", portrait = "portrait.E", gender = "female" },
  { id = "V", name = "老馆员", portrait = "portrait.V", is_victim = true },
},
victim = { id = "V", name = "老馆员" },
~~~~

- suspects 顺序 = 棋子顺序 = 卡序（见 §6）；**不要随意调整顺序**。
- id 首字符会当分享码符号（s.symbol，可用 symbol 字段覆盖）；建议 A/B/C/D/E/V。
- portrait 是**素材引用名**（UI 头像卡用），不是颜色；编辑器 assets 里要有对应 portrait.* 控件。
- gender 只被 gender_in_room 线索使用（male/female 任意字符串，只要同类可比）。
- is_victim = true 只是界面提示；权威是 victim.id。
- 受害者必须摆上盘（也占一行/列）。

### 3.6 roles / meta

~~~~lua
roles = { thief = "D" },                       -- 无同伙
roles = { thief = "D", accomplice = "C" },     -- 有同伙（规则上仍然合法；但 R4 已废止，不再是必推项）
meta = { false_clue = 4, announce = "unknown" } -- 第 4 条卡线索是假话，且不告诉玩家
meta = { announce = "none" }                    -- 全真
~~~~

- false_clue 只数**卡线索**（level.clues 数组），1 起；通用线索不在序号里。
- announce 三值都合法；但当前构建**没有任何界面出口**显示它（见 §1.5）。
- 若 false_clue 不写 ⇒ 求解器允许 0 条违反；写了 ⇒ 允许 1 条（不是必须恰好 1 条！validate_levels 才要求答案上恰好是它）。

### 3.7 solution（两种写法）

~~~~lua
-- 1) 按棋子 id（项目现用写法）
solution = { D = { r=1, c=1 }, C = { r=2, c=4 }, A = { r=3, c=2 }, B = { r=4, c=3 }, V = { r=5, c=6 }, E = { r=6, c=5 } }

-- 2) 按格
solution = { { who = "D", r=1, c=1 }, { who = "C", r=2, c=4 }, ... }
~~~~

- 两种写法 core 都认（M.new 里按 sol[1] 是否带坐标判断）。
- **运行时只在三个地方用 solution**：提示按钮 hint()、正确率 score()、失败信息里的 N/M；
  以及提交结算**不比对**（见 §1.6）。设计期 tools/dump_level / validate_levels / design_gate 会用它。
- ⚠️ solution 必须包含**所有**声明过的棋子（含受害者），同一格只能一个人；
  validate_level **不检查**这些（只检查坐标格式与 id 存在），要自己保证。

### 3.8 clues / general_clues 与「槽位」规则

- 手写 clues（推荐，也是现在两关的做法）：数组，每项 { type = ..., ... }，**顺序 = 卡序**。
  引擎的 self.clues = level.clues；核心卡数 = #clues；卡线索就是这份。
- 不写 clues（空）：Core.new 按「棋盘容量」补空槽位 { slot = i }，i = 1..min(rows, cols)
  （规则开关关掉 one_per_row/col 时退回格数 rows×cols，见 clue_slot_count :1565-1570）。
  空槽位没有 type ⇒ clue_results 报「待填内容（槽位 N）」、命中 hint 为 nil。
- general_clues：不占卡位；参与求解（design_solve 会把它们拼进线索表）与 view().general_clues；
  每条必须有已注册 type 与完整参数（validate 会报，否则「通用线索永不生效且静默」）。
- 槽位/卡数相关字段：
  · self.clue_slots = #self.clues（core:1411）
  · 视图 view().clues 条数 = #self.clues
  · tests/clue_slots.lua 断言：core.clue_slots == min(rows,cols) == piece_count；真关卡有手写 clues 时还要求
    #core.clues == clue_slot_count()，且每条 type 已注册。
- ⚠️ 副作用（坑）：validate_level 在「clues 为空」时会把 level.clue_slots 改成 rows×cols（core:1195），
  而 Core.new 自己的口径是 min(rows,cols)。两个数在正方形、开一人一行列时碰巧相等；不要依赖 level.clue_slots 字段。
- 卡线索 / 通用线索的 type 拼错：validate_level 报错（卡线索报「第 i 条线索类型未注册」，通用线索报「通用线索」字样）。

### 3.9 坐标与房间推导（速查）

- r=1 在最上、c=1 在最左。
- 房间 = walls 洪水填充（行优先扫描起点，房间号 1 起）；doors 不改变房间。
- 区域相邻 = 门两侧不同房间（双向），只扫内部边。
- 每格的四向墙/门在 view().cells[r][c].walls / .doors 里（up/down/left/right 布尔），调试时可直接看。
- 选关缩略图用 room_map.boxes(level)：每个房间一个外框 {r1,c1,r2,c2,cells}；与游戏内房间判定同一实现。

### 3.10 validate_level 到底检查什么 / 不检查什么（很重要）

M.validate_level（murdoku_core.lua:1090-1300）实际只检查：

| 检查 | 说明 |
|---|---|
| 关卡是 table | — |
| size 至少 2×2 | 不要求正方形、不要求 = 棋子数 |
| suspects 存在且 id 唯一 | — |
| victim.id 在 suspects 里（或 victim 坐标可解析） | — |
| murderer 若写则在 suspects 里 | — |
| blocked 坐标可解析 | — |
| objects 每项是 table、坐标可解析 | — |
| solution 存在、非空、id 存在、坐标可解析 | **不查行/列冲突、不查是否被 blocked、不查是否包含全部棋子、不查是否与 roles 位置一致** |
| clues：空 ⇒ 补 level.clue_slots=rows*cols；非空 ⇒ 每条必须有 type 且参数齐全、type 已注册 | 不查条数是否等于容量/棋子数 |

### 5.2 设计期求解器 tools/design_solve.lua 的精确语义

调用：local Solve = require("tools.design_solve"); local sols = Solve.solve(core, limit)

它做的事（M.solve，design_solve.lua:28-235）：

1. 线索表 = core.clues（卡线索）+ core.general_clues（通用线索）；
   若其中没有任何带 type 的线索 ⇒ 直接返回 {}（= 未测，不猜、不编）。
2. allowed = core.allowed_false（false_clue 写了 ⇒ 1，否则 0）。
3. **角色枚举** rpairs：对每个非受害者棋子 t，生成 (thief=t, accomplice=nil) 以及
   (thief=t, accomplice=a)（a 为其它非受害者棋子）。—— 它**不看 level.roles**，把角色当自由变量。
4. 摆位搜索：对每枚棋子尝试所有未占用、不 blocked、满足 one_per_row/col/room 的格；
   优先试 solution 里给的那一格（只是顺序优化）。
5. 剪枝：只对「参数里全是具体棋子、没有 @别名」的线索做边放边判；违反数 > allowed 就剪枝。
   带 @thief/@accomplice/@victim 的线索要等角色定下来才判（不参与剪枝）。
6. 叶子判定：对每个角色组合，
   a) structure_report(roles) 必须 OK（R3 + tie_policy；不含已废止的 R4）；
   b) 全部线索（含通用线索）里不成立的条数 ≤ allowed；
   ⇒ 记一个解 { placement = 二维 grid, thief, accomplice }。
7. 返回最多 limit 个解；**不比对 level.roles / level.solution**（调用方自己做）。

性能实测：case_001 全量 6 解 0.11s；case_002 全量 10 解 6.51s（6×6，limit 500）。
【已实测】剪枝只对无别名线索有效 ⇒ 想快就把线索写成「具体人名 + 局部约束」，少用 @别名。

### 5.6 历史上用过的三种唯一性判据（实测结果）

A. 标准闸门（旧「闸门 A」）：design_solve 解数 == 1，且解 = 声明答案（摆位 + thief + accomplice）。
   - case_001：6 解 ⇒ **不通过**；case_002：10 解 ⇒ **不通过**。【已实测】
   - 这是最严格、最直白的口径；对案件 003 我建议优先追它，追不上再退到 B/C。

B. 「模糊/主动因素」闸门（旧「闸门 B」，内容仓 design_gate.lua:167-261 有实现）：
   取与**全部真线索**（去掉 false_clue 那条）相容的摆位集合 S；
   对每个嫌疑人 X 记 P(X) = S 里 X 出现过的格子集合；
   判据 = 嫌疑人里**恰好一个** |P(X)| > 1（受害者 V 豁免）⇒ 那个人就是盗窃者；
   再把他代回结构闸门，要求恰好 1 个解且 = 答案。
   - case_001：摆位总数 3360；S = 2；P(A)=1、P(B)=1、P(C)=1、P(D)=2、P(V)=2（豁免）；
     ambiguous = {D}；代回结构后 1 解 = 答案 ⇒ **通过**。【已实测】
   - case_002：S = 1（真线索已经把摆位钉死）⇒ 没有模糊嫌疑人 ⇒ **判据不适用**（不能选人）。
   - 含义：这条规则本质是「**只有盗窃者还有得选**」，要求玩家用「谁的位置没被线索钉死」来锁定身份。
     数学上依赖：其他人全被钉死、只剩 1 人模糊。写关卡时要反过来设计空间与线索。

C. 「假话剔除」判据（case_002 用的约定，交接文里叫「盗窃者只剩一个可选位置时他说谎」）：
   对每张卡 i，构造 S_i = 与「除第 i 条外的全部线索（含通用线索）」相容的摆位集合；
   若**恰好存在一个 i** 使 |S_i| 非空（其余为 0），则第 i 条是假话，其说话人 = 盗窃者。
   - case_002 实测：去掉第 1/2/3/5/6 条都得 0 个相容摆位；只有去掉第 4 条（above）得 1 个
     ⇒ 假话 = 第 4 条（其说话人是 D）⇒ 盗窃者 = D，与声明一致。【已实测】
   - 含义：线索集在「全部为真」时矛盾，且只有去掉一条才自洽 ⇒ 玩家可用排除法抓假话。
   - 适用条件：其它真线索必须强到「少一条就无解」，否则 |S_i| 会 >1 或出现多个候选。

D（补充）. 摆位唯一性（比 A 弱，但比「完全不查」强）：
   design_solve 解里不同摆位数 == 1 且 = solution。
   - case_001 / case_002 都满足（实测 distinct placements = 1）。
   - 对本作玩法（提交只认摆位、身份自动揭示）来说，这条已经够玩家体验；角色层唯一是加分项。

   因为 announce 已无界面出口，玩家不会被提前告知有假话。
5. **6 条卡线索**（不是 5 条、不是 7 条）：clue_slots 测试要求手写条数 == min(6,6) == 6；
   想多放事实就用「复合类型」（像 case_002 的 alone_and_below_in_other_room）塞进一句，或走通用线索。
6. **别碰的线索类型**：left_of/right_of/above/below/between/beside/in_front_of/with_victim/distance=1
   （恒假，只能当假话）；not_beside/only_one_in_row（恒真，等于没写）。

### 5.8 建议的闸门脚本（可直接落地为 tools/design_check.lua）

> 我在实验副本里用同构逻辑做过逐项验证（probe2/probe3/probe6），下面的整合版是按同一口径写的；
> 本次任务不往实现仓加文件，故只在这里给出。落地时放在 qianxing-murdoku/tools/ 下，仓库根目录跑：
> lua tools/design_check.lua [case_003]

~~~~lua
-- tools/design_check.lua —— 设计期闸门：格式 + 结构R3 + 答案假话 + 闸门A(解数=1且=答案)
package.path = table.concat({ "lua/?.lua", "lua/?/init.lua", "?.lua" }, ";")
local Core = require("murdoku_core")
require("tools.design_rules")            -- 结构规则只在设计期存在
local Solve = require("tools.design_solve")  -- 求解器只在设计期存在
local Levels = require("levels.init")

local function grid_key(g, rows, cols)
  local t = {}
  for r = 1, rows do
    for c = 1, cols do
      if g[r][c] then t[#t + 1] = g[r][c] .. "(" .. r .. "," .. c .. ")" end
    end
  end
  table.sort(t)
  return table.concat(t, " ")
end

local function answer_grid(lv, rows, cols)
  local g = {}
  for r = 1, rows do g[r] = {} end
  for id, p in pairs(lv.solution or {}) do
    if type(p) == "table" and p.r and p.c then g[p.r][p.c] = id end
  end
  return g
end

local function check_level(lv)
  local fails = 0
  local function bad(msg) fails = fails + 1; print("  [FAIL] " .. msg) end
  local ok, errs = Core.validate_level(lv)
  if not ok then
    bad("格式：" .. table.concat(errs or {}, " / "))
    return fails
  end
  local core = assert(Core.new(lv))
  for id, p in pairs(core.solution) do
    core:select_suspect(id)
    core:hold_cell(p.r, p.c)
  end
  local sok, serrs, sinfo = core:structure_report()
  print(string.format("  结构：%s  受害者区域 #%s k=%d 相邻[%s] 无辜最多 %s",
    sok and "OK" or "FAIL", tostring(sinfo.victim_room), sinfo.k or 0,
    table.concat(sinfo.adjacent or {}, ","), tostring(sinfo.best)))
  if not sok then
    for _, e in ipairs(serrs or {}) do bad(e) end
  end
  local res = core:clue_results()
  local failed = {}
  for i = 1, #res do
    if res[i].type and not res[i].satisfied then failed[#failed + 1] = i end
  end
  local lie = tonumber((lv.meta or {}).false_clue)
  if lie then
    if not ((#failed == 1) and (failed[1] == lie)) then
      bad("假话：声明第 " .. lie .. " 条，答案上不成立 [" .. table.concat(failed, ",") .. "]")
    end
  elseif #failed ~= 0 then
    bad("未声明假话但答案上有 " .. #failed .. " 条不成立")
  end
  local sols = Solve.solve(core, 50)
  local ans = grid_key(answer_grid(lv, core.rows, core.cols), core.rows, core.cols)
  local a_ok = (#sols == 1)
    and (sols[1].thief == lv.roles.thief)
    and (sols[1].accomplice == lv.roles.accomplice)
    and (grid_key(sols[1].placement, core.rows, core.cols) == ans)
  print(string.format("  闸门A：解数 %d（上限 50）%s", #sols,
    a_ok and "  OK 与声明答案一致" or "  FAIL"))
  if not a_ok then fails = fails + 1 end
  local seen, np = {}, 0
  for _, s in ipairs(sols) do
    local k = grid_key(s.placement, core.rows, core.cols)
    if not seen[k] then seen[k] = true; np = np + 1 end
  end
  print(string.format("  摆位唯一性：%d 个不同摆位", np))
  return fails
end

local only = arg and arg[1]
local n, bad = 0, 0
for _, lv in ipairs(Levels.all()) do
  if only == nil or only == lv.id then
    print("\n— " .. tostring(lv.id) .. "  " .. tostring(lv.name or ""))
    n = n + 1
    bad = bad + check_level(lv)
  end
end
print(string.format("\n%d 关，%d 项未通过", n, bad))
if bad > 0 then os.exit(1) end
~~~~

case_001 报 6 解 FAIL、case_002 报 10 解 FAIL、case_003 报 0 解 FAIL（与 §5.4 一致）；
脚本可加载、无运行时错误。【已实测】

## 六、6×6 的卡位 / 线索条数约束、卡序与说话人规则

### 6.1 卡位与条数（6×6 专属数字）

| 项 | 值 | 依据 |
|---|---|---|
| 棋盘 | 6×6 | 本案要求 |
| 棋子数 | 6（A/B/C/D/E + 受害者 V） | 设计约定「#棋子 == rows == cols」；tools/new_level 强制、tests/clue_slots 查 |
| 卡位（卡线索） | 6 | = min(rows,cols) = 棋盘容量 = 棋子数 |
| 手写 clues 条数 | 必须正好 6 | tests/clue_slots.lua:105-107（#core.clues == clue_slot_count）；多一条/少一条会红 |
| 通用线索 | 不占卡位，可 0 或 1 条（当前全作唯一一条在 case_002） | core:general_clues |
| 界面控件生成上限 | 18 条 | ui_controller.LAYOUT.clue_max_visible = 18（:161） |
| 网格视窗一屏可见 | 4 条（可滚动；cfg 544 高、item 96、间距 8、padding 20） | docs/线索区-内容填入规则.md §四；非 clue_rows/clue_row_h 老路径 |
| 头像卡容量 | 角色 ≤ 16 | tests/ui_math.lua:320（当前 6 人绰绰有余） |
| 编辑器内容行 | row.3.1 … row.3.6（6 行） | 行号 = LIST 下标（见 §6.4） |

- 若写的 clues 少于 6：clue_slots 测试红；且卡序会与棋子错位（第 k 张卡选中的仍是第 k 枚棋子，但线索只有 k<n 条时，
  后面几张卡没有线索内容 ⇒ 高亮/文案全空）。
- 若写的 clues 多于 6：卡数 > 棋子数，clue_slots 红；界面虽能显示（≤18），但「一人一条」的设计被破坏。
- 通用线索会让网格列表**多一项**（在列表最上方，pos=1），普通卡从 pos=2 起映射到第 1..6 张；代码已处理这个偏移
  （_fill_grid_item 6140-6147）。加通用线索不会影响 6 张卡的映射，但编辑器要配 row.3.clue（见 §6.5）。

### 6.2 卡序 = 棋子序 = 线索序（硬约束）

- 卡 k ↔ level.clues[k] ↔ core.pieces[k] ↔ suspects[k] ↔ 编辑器 row.<关>.k。
- 代码证据：
  · Controller._piece_at_row(core, n) = core.pieces[n].id（ui_controller.lua:4777-4792）；
  · 点第 k 张卡 → _person_id_for_pos(k) = 第 k 枚棋子（7580-7598）；
  · 高亮/位置提示：focused_clue = 选中棋子所在行号；clue_hint(focused_clue) = 第 k 条线索的提示（7632-7643, 7649+）；
  · tests/clue_slots.lua §7 断言「卡上配 id 或显示名都 ⇒ 选中第 pos 个棋子（who 不参与）」。
- 推论：如果 level.clues 顺序与 row 区内容顺序不一致，会出现「卡 k 显示的是 A 句，但高亮的是 B 句允许格」的错位；
  这种错位在离线测试里基本抓不到（row 内容是存档数据），只能靠设计纪律 + 真机核对。
- **不要重排 suspects**：重排 = 同时改卡序、行号、字母映射、行内容映射；除非同步改编辑器 row 区。

### 6.3 说话人规则（谁说的 ≠ 线索主体）

- 本作的卡片模型（沿用 Murdoku）：每人一张卡；卡上显示**说话人的头像与名字** + 一句陈述。
  陈述可以讲任何人（例：当前 case_001 的卡 1 由 A 说，内容是「收藏家 在第5列」）。
- 引擎**没有「说话人」字段**：它只认卡序 ↔ 棋子序；说话人完全由编辑器 row.<关>.<k> 的 who/face 决定。
- 因此：
  · level.clues[k] 必须与 row.<关>.<k>.what 的句子是**同一条线索**（内容与参数一致）；
  · row.<关>.<k>.who / .face 是「第 k 枚棋子」的显示名与头像（约定：说话人 = 第 k 枚棋子）；
  · 主体是谁由线索参数决定，可以不是第 k 枚棋子。
- 线索内容里用 @thief/@accomplice/@victim 时，卡片只显示「盗窃者/同伙/受害者」字样（ctx.name 的 ROLE_WORDS），
  不会泄露真名（core:227-235）；编辑器 row 文案里也要注意别手滑写真名。

### 6.4 row.<关>.<行> 四槽位契约（卡片显示的权威来源）

编辑器内容源：assets/row.<关>.<行>（容器）下四个槽位控件：

| 槽位 | 含义 | 例子 | 代码落账与使用 |
|---|---|---|---|
| who | 卡片左侧**人名**（说话人显示名） | 值夜保安 / A（都行；显示用） | _row_text[关][行].who；卡片 who 控件 |
| what | **线索正文**（一句话） | 收藏家 在第 5 列 | 卡片 what 控件 |
| letter | 该行**棋子**在棋盘上的标记字母（笔记/棋盘标记用） | A 或 a 或 L1 | _row_letter[人物id]；棋盘 note 显示 |
| face | 该行棋子的**头像素材名** | portrait.A | _row_face / 卡片 face 图片；tray 头像另走 suspects.portrait |

- 落账在 _fill_grid_item（ui_controller.lua:6214-6360 附近）：只填一次（先到先得），换关时
  _reset_row_maps_if_level_changed 整体清空（:373-406）。
- 卡片四样取值在 _grid_text_payload（:5718-5837）：row 内容优先；缺 who/what 时回退「从引擎线索文案里切人名」；
  缺 letter 时回退该棋子 id；缺 face 时回退 tray 的 portrait。
- **who 不再参与棋盘线**（2026-10-11 用户定案）：点卡选谁只由「第几张卡 = 第几枚棋子」决定，who 只影响显示。
- 注意：四槽位是**按关序 + 行号**记的；行号 = LIST 下标。改 LIST 顺序/插关 ⇒ row 内容全部错位。

### 6.5 通用线索卡（不属于任何人的卡）

- Lua 数据：general_clues = { { type = "nobody_on_object", object = "地毯" } }；不占卡位；参与求解与校验。
- 界面：网格列表在最上方多一项（pos=1）。**判据是编辑器内容源存在**（_has_general_clue，:5968-5982）：
  先找 row.<关>.clue 容器 → 有 = 有通用线索；找不到才退回看 core.general_clues 是否非空。
- 正文来源：row.<关>.clue 容器 → FindChild("clue.<关>.1") 的 text（_fill_general_item，:5984-6044）；
  gen.title 的标题文案在模板里预先填好，脚本只写 gen.body。
- 点击通用卡只发 focus_general（只做提示高亮），不选人、不参与放置；提示用 clue_hint_general(1)（只看第 1 条）。
- 结论（坑）：若你的 6×6 关想加通用线索，需要三件事同时做：
  ① 关卡 Lua 里写 general_clues（类型+参数要合法）；② 编辑器建 row.3.clue 容器并在 clue.3.1 里写正文；
  ③ 接受列表多一项。只做①不做②：列表仍会显示通用卡（_has_general_clue 退回 core.general_clues），但正文空白。
  只做②不做①：会显示一张空的通用卡（判据是内容源），且它不参与求解。

### 6.6 announce 的现状（内容设计要注意）

- meta.announce = none / one / unknown 都合法，但当前构建**没有任何界面出口**显示它
  （副标题控件 2026-10-18 删除；关卡内 toast 也无处显示）。【读代码推断】
- 所以：
  · announce=none 的「线索全部为真」不会显示；
  · announce=unknown 的「不告诉玩家」与 one 的实际表现当前**没有差别**；
  · 依赖「玩家事先知道有几条假话」的设计目前不可行；假话必须能从矛盾中自己发现（C 型设计）。
- 这些是产品缺口，不是关卡数据问题；如果用户要求恢复，需要新开控件位（不要接回 hud.subtitle）。

### 6.7 6×6 规模与性能数字

- 摆位空间：6! × 6! = 720 × 720 = 518400（完整排列）。
- 求解器实测：case_002 全量枚举 10 个解耗时 6.51s（Lua 5.4.6，实验副本）；limit 越小越快；
  别名线索不参与剪枝 ⇒ 别名越多越慢。
- 关卡设计期的闸门脚本建议用 limit 50（足够判断唯一性；不要用 2，太小会掩盖多解）。
- 编辑器几何/素材容量对 6×6 不是问题（界面自适应网格边长与头像卡列数）。

### 6.8 卡片交互（与设计相关的行为）

- 点卡：选中卡上那个人（第 k 张 = 第 k 枚棋子）；再点同一张 = 取消选中。
  高亮由 core.selected 派生，不另存状态。
- 选中某人 ⇒ focused_clue = 那个人所在卡位 ⇒ 棋盘上按该卡线索的「允许位置」亮提示格
  （见 §2.12）；人对人线索不亮。
- 灰白层由 core.placed[人物id] 决定（已正式放置的卡变灰）；预放置不算 placed。
- 卡片内容与线索类型不一致时：提示格会按 level.clues[k] 算，而玩家读到的是 row.<k>.what
  ⇒ 玩家会觉得「提示不对」。这是内容错位最直观的症状。

### 7.1 先定这 10 件事（设计决策清单）
